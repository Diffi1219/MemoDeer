# MemoDeer 模型使用全景

## 模型总览

| 模型 | 运行位置 | 网络需求 | 用途 |
|------|----------|----------|------|
| **Embedding** `BAAI/bge-small-zh-v1.5` | PC 本地 CPU | 仅首次下载 | 文本→向量（语义搜索的基础） |
| **Flash** `deepseek-v4-flash` | DeepSeek 云端 API | 每次调用 | 轻量 NLU：文档 AI 格式化（原始文本→结构化 Markdown） |
| **Pro** `deepseek-v4-pro` | DeepSeek 云端 API | 每次调用 | 强推理：RAG 知识库问答 + 降级自由问答 + 知识点提取（会员） |

## 各模型详解

### 🟢 Embedding 模型 — 语义理解的基石

```
模型：BAAI/bge-small-zh-v1.5
大小：~95MB
维度：512
运行：PC 本地 CPU（sentence-transformers）
速度：毫秒级
成本：零（无 API 调用）
```

**在整个流程中参与了 3 个环节：**

| 环节 | 输入 | 输出 | 调用方法 |
|------|------|------|----------|
| 文档上传 | 所有分块文本（列表） | 512 维向量列表 | `embedding_service.embed()` |
| 知识库问答 | 用户问题（单条） | 512 维向量 | `embedding_service.embed_query()` |
| 语义搜索 | 搜索关键词（单条） | 512 维向量 | `embedding_service.embed_query()` |

**为什么用本地模型？**
- 向量化是高频操作（每个文档分块、每次提问都要做）
- 如果每次调云端 Embedding API，延迟高 + 有费用
- BGE-small 只有 95MB，CPU 就能跑，毫秒级响应
- 缺点是首次启动需要下载模型文件（国内走 hf-mirror.com 镜像）

**加载优先级**：本地目录 → HF 缓存 → 网络下载（详见 `embedding_service.py`）

### 🟡 Flash 模型 — 文档 AI 格式化

```
模型：deepseek-v4-flash（可切换为本地 qwen3:8b）
位置：DeepSeek 云端 API
温度：0.3（低，保证格式化输出稳定）
费用：便宜（轻量模型）
```

**在整个流程中只参与了 1 个环节：**

| 环节 | 输入 | 输出 | 调用位置 |
|------|------|------|----------|
| 文档上传后处理 | 从 PDF/DOCX 提取的原始文本 | 结构化 Markdown（含标题层级、列表、粗体等） | `_reformat_text_to_markdown()` |

**格式化做了什么？**
- 给纯文本添加 `# ## ###` 标题层级
- 识别列表转为 `- ` Markdown 列表
- 用 `**粗体**` 标记重要术语
- 修复 OCR/提取导致的错别字和多余换行
- 保持原文信息不丢失、不篡改

**为什么用 Flash？**
- 文档格式化是"阅读理解 + 结构化改写"，不需要强推理
- Flash 完全够用，比 Pro 便宜很多
- 还可通过 `use_local_for_flash()` 切到本地 Ollama 8B，完全零成本

### 🔴 Pro 模型 — 核心问答引擎

```
模型：deepseek-v4-pro
位置：DeepSeek 云端 API
温度：0.7（中等，平衡准确性和创造性）
费用：较贵（最强推理模型）
```

**在整个流程中参与了 3 个环节：**

| 环节 | 输入 | 输出 | 调用位置 |
|------|------|------|----------|
| RAG 知识库问答 | 检索到的文档上下文 + 用户问题 | SSE 流式回答（带引用标注 `[1][2]`） | `stream_answer()` |
| 降级自由问答 | 用户问题 + 免责声明 | SSE 流式回答（无引用，标注"非来源于笔记"） | `stream_answer_fallback()` |
| 知识点提取（会员） | 笔记本全部文档内容 | JSON 知识点 `[{title, content, tags}]` | `extract_knowledge_points()` |

**问答流程（自动智能模式）：**
```
用户提问 → Embedding 向量 → ChromaDB 检索 Top-8
                                      │
                    ┌─────────────────┴─────────────────┐
                    ▼                                   ▼
          有相关结果（距离 < 0.5）              无相关结果（距离 ≥ 0.5）
                    │                                   │
                    ▼                                   ▼
            Pro RAG 上下文回答                   Pro 降级自由回答
            带引用标注 [1][2]                   开头说明"非来源于笔记"
            source="rag"                       可保存为笔记
                                               source="open"
```

**为什么问答都用 Pro？**
- RAG 问答需要：理解问题意图 + 综合多个文档片段 + 逻辑推理 + 生成连贯回答
- 这是典型的强推理任务，Flash 做不了这么复杂的综合推理
- Pro 才能保证"基于多段上下文给出准确、有逻辑的回答"

## 关键设计决策

| 设计决策 | 原因 |
|----------|------|
| 问答默认自动模式（非手动选择） | 简化交互：先 RAG 后降级，用户无需关心是否命中知识库 |
| Embedding 放本地 | 高频调用，本地零延迟零成本 |
| Flash 做文档格式化（云端可切本地） | 中频调用（上传时），云端方便，想省钱可切本地 8B |
| Pro 始终保持云端 | 每次提问都依赖推理质量，必须用最强模型 |
| 降级自由问答带免责声明 | 用户需知道回答不是来自自己的笔记，需要甄别真伪 |
| 降级回答可保存为笔记 | 用户可将有价值的 AI 回答存入知识库，下次可被 RAG 检索 |
| 知识点提取是会员功能 | 额外 Pro LLM 调用成本，作为 VIP 增值服务 |
